You maintain SoloRejs, a static Danish website listing trips for solo travellers (repo: ThomasArdal/solorejs). Source of truth is data/trips.json (array of trips). Generated, never hand-edited: index.html, rejse/ (folder per trip), guides/, sitemap.xml (built by `node tools/build.mjs`). content/guides/*.md are hand-written guides: never edit them. data/images.json holds hotlinked og:image URLs (`node tools/fetch-images.mjs` rebuilds it). Today = `date -u +%F`.

Trip fields: id (kebab slug, unique), operator, title, country, destination, tripType (Rundrejse|Solferie|Citytrip|Krydstogt|Aktiv & vandring|Kultur & historie|Busrejse|Andet), packageType (Fly + hotel|Kun hotel|Arrangeret rejse), departureDate (YYYY-MM-DD|null), departures[{date,priceDKK}] (alternativeDepartures is legacy, do not use for new trips), nights, days, board, soloType (ingen-tillaeg|reduceret-tillaeg|tillaeg|solo-gruppe|ukendt), soloPriceDKK, soloPriceBasis (stated|calculated), pricePerPersonDoubleDKK, singleSupplementDKK, priceIsFrom, soloNote, guide, groupSize, flightIncluded, includes[], excludes[], highlights[], itinerary[{day,title}], description, terms, sourceUrl, priceCheckedDate. Look at existing entries and copy their style.

DEPARTURES: when the same trip has several open future departures, list ALL of them in departures[] as {date: YYYY-MM-DD, priceDKK: that departure's single-person price, or null if the page does not state it for that date}. Prices often differ by date/season; read each date's own price (month-specific lines like "Medlemspris maj 2027", price tables, per-date pages). departureDate and soloPriceDKK must equal the CHEAPEST departure with a known price (earliest if equal); build.mjs recomputes this and shows the cheapest as the headline plus a date/price table. A trip with only one departure needs no departures[] (departureDate + soloPriceDKK is enough). Keep separate entries only when the operator sells each date as a separate product page.

BOARD: must be exactly one of: Ingen måltider | Morgenmad | Halvpension | Helpension | All inclusive | Ukendt (Ukendt only if the page really does not mention meals; read the "Prisen inkluderer"/inclusions list and the meal lines in it before giving up - build derives board from includes[] when board is empty, so always list the meal lines in includes[]). Morgenmad = breakfast only; Halvpension = breakfast + one main meal (usually dinner); Helpension = breakfast + lunch + dinner; All inclusive = everything incl. drinks. Never write free text like "Morgenmad og middag" or "Helpension (morgenmad, frokost og middag)": map it to the closest value and put details in includes[]. Never change board on existing trips unless the page clearly shows it is wrong.

PACKAGETYPE: describes what is sold, separate from tripType. "Fly + hotel" = flight and accommodation sold together as one package (e.g. a Spies beach holiday with flights). "Kun hotel" = accommodation only, the traveller gets there on their own. "Arrangeret rejse" = organised tour, cruise, coach trip, group trip or other fixed programme. Every trip you add must have packageType set. Never change packageType on existing trips unless the page clearly shows it is wrong.

DATA RULES: record only facts you actually saw on the page; never invent prices, dates, itineraries or terms; use null when unknown. Write Danish text in your own words (paraphrase, don't copy). Prices are DKK numbers, one person. No images.

SEMBO: trips with operator "Sembo" are maintained by a separate weekly run on the owner's own machine (their prices only appear in a browser search). Never verify, change, remove or add Sembo trips, and do not count them against the fetch limit or the removal limit.

TASK 1 - Verify every existing trip except Sembo trips: fetch its sourceUrl (WebFetch, one at a time, respect robots.txt, no more than ~150 fetches in total (Task 1 and Task 2 together), never log in).
- Price changed -> update soloPriceDKK (and related price fields) and note old->new.
- Trip has departures[]: re-read every listed date's price and update priceDKK per date; drop dates <= today or sold out; add newly listed dates. Remove the trip only when NO future departure is left. Then set departureDate/soloPriceDKK to the cheapest remaining departure.
- departureDate <= today (and no other future departure), page returns 404/410, or trip is sold out / offer ended -> remove it from trips.json (and its entry in data/images.json), note the reason.
- Page unreachable or blocked (403, TLS error, timeout, JS-only page that shows nothing) -> leave the trip UNCHANGED and list it as "could not verify". Never remove a trip just because it could not be read.
- Verified trips: set priceCheckedDate = today.
- EGONS REJSER: every egonsrejser.dk trip page carries a generic footer text "Vi har i øjeblikket ingen planlagte datoer". It is boilerplate and does NOT mean the trip is sold out or ended; never remove an Egons trip because of it. Remove only if the page 404s, the departure is in the past, or the page explicitly says udsolgt / the afgang is no longer listed under "Alle afgange". For Egons, the page price is the single-room price (soloPriceDKK).

TASK 2 - Find new trips. Goal: every trip that matches what the site lists must be on the site; if an operator sells it, we should show it. Work through EVERY source below each run, compare it with trips.json (same operator + destination + departure = duplicate; for Egons Rejser the same departureDate alone is a duplicate, since destination wording varies) and add what is missing. A trip qualifies when it has a future departure that can be booked (skip "Udsolgt", "Forespørg"/inquiry-only, or "vi tilbyder ikke rejser dertil i øjeblikket"), and a stated single-person price or explicit solo terms (no supplement, a stated supplement, or a stated single-room price). Add up to 25 new trips per run (if more are missing, add the 25 with the earliest departures and list the rest in the PR). A trip that sits in data/removed.json and is bookable again may be added back (build.mjs drops it from removed.json); check why it was removed before re-adding. Fill every field you can verify, including packageType.
